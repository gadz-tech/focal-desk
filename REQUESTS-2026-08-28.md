## 1 · BUG — Fusion 360 never tiles; it floats

**Ryan's words:** "Autodesk Fusion never snaps anywhere. It floats around like
the Windows snip copy-paste window (snip *should* work like that, but Fusion
should not). It might be because it opens a loading screen first before going
to the full app."

- Snip's floating is **correct** (ignore/unmanageable path) — don't "fix" that.
- Ryan's splash-screen theory fits the code: `win::is_manageable` is
  deliberately conservative ("a window that cannot be resized cannot be
  tiled"), and splash windows are typically borderless/unresizable. Two
  candidate mechanisms to check, not assume:
  a. The main window is a **new HWND** arriving after the splash — then why
     doesn't the 400 ms rescan pick it up? (Style check timing? Parent/owner
     chain? Class name in an ignore rule?)
  b. Fusion **reuses the splash HWND** and swaps styles once loaded — then
     `is_manageable` was evaluated once at open and never re-evaluated, and
     the cached frame insets (measured once, for the life of the window —
     ARCHITECTURE.md invariant) may also be stale.
- Lane definition of done: Fusion's main window tiles; the splash stays
  ignored; an engine/adapter test pins "a window that becomes manageable
  later gets managed." Start with `log.rs` output during a Fusion launch —
  observe which mechanism it actually is before touching code.

## 2 · FEATURE — border/tab as manual focus activator; retire the dwell delay

**Ryan's words:** "I don't like the 1.35 s delay when clicking on something.
We need a border around each window which can be a manual focus activator —
all the way around, or maybe a tab that is always facing the center of the
screen. It has to be pretty big so I can tap it easily. This gets rid of the
reason for the 1.35 s delay and allows me to interact more with windows out
of focus."

- The delay is `dwell_ms = 1200` (config.rs default; perceived ~1.35 s — the
  400 ms rescan tick can add up to one tick on top). It exists because
  activation is currently the *only* gesture — dwell is how the engine tells
  "using a window" from "passing through."
- The proposal splits the two on purpose: plain click into a window =
  interact, **no promotion**; tap on the border/tab = explicit promote. That
  is architecturally the blessed seam — ARCHITECTURE.md: "add a promotion
  gesture (hotkey, gaze, …) → adapter only — it just sends `Promoted`."
- Geometry: full perimeter, or a tab always facing screen center — Ryan's
  open choice; either way **big enough to tap easily**. Size in inches, not
  px, like the gutter (physical quantity on the 65"/8K panel). The gutter
  channels (windows sit one gutter apart) are the natural place for the
  border to live without covering content; renderer could ride the planned
  wallpaper/wires layer.
- Open decisions for the lane (don't decide in the capture): does dwell stay
  as a configurable fallback (`dwell_ms = 0` = off?) or go entirely; does
  clicking a window body still restart any timer at all; hit-testing for the
  tap target (a real layered window per managed window vs wallpaper-layer
  hit region).
